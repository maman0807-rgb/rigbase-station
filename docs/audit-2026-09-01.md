## 🔴 Kritis — risiko korupsi data riil

### 1. Antrian offline Input Harian/WO/Request tidak punya proteksi duplikat
**Repo**: `logbook-equipment` · **Commit terkait**: `6227e17` (sehari setelah Fase 27 yang justru menambah proteksi ini untuk `logbook`/`hm_photo_reports`)

- `src/contexts/OfflineContext.jsx` `syncPending()`: untuk tipe `dailyLog`/`workOrder`/`request`, panggil `addDailyLog()`/`createWorkOrder()`/`addRequest()` lalu baru `deletePendingSubmission()` setelah sukses. Kalau response network hilang setelah insert/RPC commit di server tapi sebelum ack sampai ke client (umum di mobile), item tetap di antrian IndexedDB dan di-retry (event `online` ATAU interval 90 detik) → **submit dobel yang benar-benar tereksekusi 2x di server**.
- Diverifikasi live: tabel `daily_logs`, `work_orders`, `operator_requests` **tidak punya kolom `client_ref_id`** sama sekali (cuma `logbook` dan `hm_photo_reports` yang punya, dengan unique index non-partial dari Fase 29).
- `src/supabase/maintenanceLogs.js` `addDailyLog()` → panggil RPC `add_daily_log_atomic` langsung, tanpa dedup key.
- `src/supabase/workorders.js` `createWorkOrder()` → `.insert()` langsung, tanpa dedup key.
- `src/supabase/operatorRequests.js` `addRequest()` → `.insert()` langsung, tanpa dedup key.

**Skenario gagal paling parah**: mekanik isi Input Harian pakai spare part secara offline, sync jalan, RPC `add_daily_log_atomic` sukses potong stok, tapi konfirmasi ke browser gagal sampai (app dibunuh/tab ditutup/sinyal putus persis di momen itu) → item tetap di antrian → retry berikutnya **memotong stok yang SAMA sekali lagi** dan bikin baris `daily_logs` duplikat. Bukan cuma duplikat record kosmetik — ini **korupsi stok riil**, gejalanya identik dengan pola double-submit yang sudah diperbaiki fleet-wide 2026-08-14, tapi celah baru dibuat lagi di commit yang sama yang memperbaiki masalah lain. WO/Request risikonya lebih ringan (duplikat record administratif, tidak ada efek samping data numerik).

**Rekomendasi fix**: tambah `client_ref_id` (uuid, unique index non-partial) ke `daily_logs`, `work_orders`, `operator_requests`, generate di client (persisted across retry), pakai `upsert(onConflict:'client_ref_id', ignoreDuplicates:true)` — pola sama persis Fase 27.

## 🔴 Kritis — celah akses data sensitif

### 2. Operator biasa bisa baca SEMUA laporan PEKA se-perusahaan
**Repo**: `logbook-equipment` · **File**: `PekaRekapPage.jsx`, route `/operator/peka/rekap` (`App.jsx:178-180`, dapat diakses role `operator` biasa)

- `peka_reports_migration.sql`: `peka_reports_select ON peka_reports FOR SELECT TO authenticated USING (true)` — tidak ada pembatasan RLS sama sekali.
- Di eRAMHoist, halaman PEKA sengaja digerbang `srOnly: true` (`index.html:342`, `isSrMekanikOrAbove()`) — niatnya data ini khusus Sr Mekanik+ (SPV/HSE), per commit message `8eabed3`.
- Tapi `PekaRekapPage.jsx` memanggil `getPekaReports()` **tanpa filter reporter** — ambil SEMUA laporan dari semua operator, termasuk `catatan_tindak_lanjut` (bisa berisi komentar sensitif soal insiden/kesalahan orang lain).

**Kontradiksi langsung** dengan pembatasan Sr-Mekanik+ di sisi admin untuk data yang sama persis.

**Rekomendasi fix**: putuskan dulu kebijakan yang diinginkan (operator cuma boleh lihat laporannya sendiri? atau semua boleh lihat rekap tapi tanpa catatan tindak lanjut?), lalu terapkan filter di `PekaRekapPage.jsx` dan/atau perketat RLS `peka_reports_select`.

## 🟡 Sedang

### 3. Laporan PEKA bisa tercatat dobel
**Repo**: `logbook-equipment` · **File**: `src/supabase/pekaReports.js:16-31` (`addPekaReport`)

`.insert(row)` polos, tanpa `client_ref_id` + upsert — kelas bug yang sama dengan temuan #1, PEKA dibangun 30 Agustus (setelah Fase 27) jadi tidak dapat proteksi yang sama. Skenario: operator submit saat sinyal lemah → row ter-insert di server, response timeout di client → retry → laporan accident/incident sama tercatat 2x (mempengaruhi statistik kategori & leaderboard).

### 4. Audit trail stok tidak akurat saat pemakaian part melebihi stok tersedia
**Repo**: `rigbase-station` · **File**: `fase30_daily_log_atomic.sql` (`add_daily_log_atomic`/`update_daily_log_atomic`/`delete_daily_log_atomic`)

`v_stok_sesudah := GREATEST(0, COALESCE(v_stok_sebelum,0) - v_rec.delta)` — kalau pemakaian part melebihi stok yang ada, `stok_sesudah` di-clamp ke 0, TAPI baris `stock_transactions` yang diinsert tetap mencatat `jumlah = ABS(v_rec.delta)` (angka diminta, bukan angka yang benar-benar diterapkan). Contoh: stok=5, delta=+10 → `stok_sesudah`=0, tapi transaksi bilang "keluar 10, stok_sebelum 5, stok_sesudah 0" (5-10≠0). Kalau nanti perlu rekonsiliasi/audit histori stok dari `stock_transactions`, angkanya tidak akan cocok dengan kondisi riil.
